# MC 26.2 rendering notes

Client-rendering techniques and traps found while building `log-all-the-things` (window/carpet/snow
logging), `camel-nostrils` (upside-down beds) and others. Decompiled vanilla source for the classes named
here is cached under `.sources/minecraft/26.2/` (see the `mc-source-decompile` skill). For z-fighting see
[gotchas/rendering.md](agents/gotchas/rendering.md).

## Rendering a second block inside a block entity renderer

26.2 has a loader-agnostic way to draw an extra full block model at any position from a
`BlockEntityRenderer`, with correct lighting, AO and biome tint: build a `MovingBlockRenderState`
(`randomSeedPos`, `blockPos`, `blockState`, `biome`, `cardinalLighting`, `lightEngine`; copy
`cardinalLighting()` / `getLightEngine()` from the real `ClientLevel`) and call
`submitNodeCollector.submitMovingBlock(poseStack, state, 0)` inside `submit(...)`. Vanilla's
`PistonHeadRenderer` uses the same mechanism. It replaces the old Forge-era approach (custom `BakedModel`
merging quads from two models, plus a z-fighting hack) with a few lines and no mixins.

Two related traps (see `log-all-the-things`' `windowlog.WindowedBlock`):

- `RenderShape` only has `MODEL` and `INVISIBLE` now. `BlockEntityRenderDispatcher` picks a renderer purely
  by block-entity type, so a block drawn entirely by its renderer should declare `RenderShape.INVISIBLE`.
- A `Block` built from a hand-made `BlockBehaviour.Properties` (not `ofFullCopy`, not chimeric-lib's
  `BlockConfig`) throws `NullPointerException: Block id not set` from `Properties#effectiveDrops()` unless
  you call `.setId(ResourceKey.create(Registries.BLOCK, id))` before `super(...)`. See minekea's
  `ShelfBlock` constructor.

### `submitMovingBlock` loses ambient occlusion

`MovingBlockRenderState.getBlockState(pos)` returns air for every position except its own `blockPos`, and
the AO pass queries it for every neighbor. So a block drawn through `submitMovingBlock` gets **zero AO,
permanently**. That is fine for a piston's briefly-detached block, but it makes a permanently placed
substitute block look flatter and brighter than the same block placed normally (most visible under
leaves). Fix: subclass `MovingBlockRenderState` (non-final, public fields) and delegate
`getBlockState` / `getFluidState` to the real `ClientLevel` for every position except the render's own
`blockPos`. `getHeight()` / `getMinY()` need no override. Implemented as
`log-all-the-things`' `client.RealNeighborMovingBlockRenderState`, used by the window- and carpet-logging
renderers. Any new "logged"/substitute-block feature needs the same subclass.

Call chain, if you need to trace it: `submitMovingBlock` -> `MovingBlockFeatureRenderer.buildGroup` ->
`ModelBlockRenderer#tesselateBlock` -> `BlockModelLighter#prepareQuadAmbientOcclusion`.

## Custom quad geometry from a hand-authored JSON model

`submitMovingBlock` only draws a real `BlockState`'s model. For hand-cut shapes (e.g. glass following a
stair notch), parse the Blockbench `elements` (cuboid `from`/`to`, per-face `uv`/`rotation`/`texture`)
into a small record model, then call `SubmitNodeCollector#submitCustomGeometry(poseStack, renderType,
CustomGeometryRenderer)` and emit 4 `VertexConsumer` vertices per face
(`addVertex(pose, x, y, z).setColor(...).setUv(...).setLight(...).setNormal(...)`). Working examples:
`windowlog.client.WindowFrameRenderer` and minekea's `GlassJarFluidRenderCommandQueue`.

Failures here are silent (nothing renders, or you get "rainbow" atlas garbage). Check these first:

- **UV scale.** `TextureAtlasSprite#getU(offset)` / `getV(offset)` take a 0-1 fraction of the sprite, not the
  model JSON's 0-16 pixel units. Divide every JSON `uv` by 16.
- **Texture slot keys.** Blockbench numbers texture slots by creation order, not role (`"1"`/`"2"` in one file,
  `"4"`/`"5"` in another). Resolve each **face's** own `texture` reference to its value and compare the
  value against your placeholders (`block/glass`, `block/glass_pane_top`); never pick one canonical key up
  front. Blockbench often sets `particle` to the same value as the main face texture, so a value-to-key
  lookup is ambiguous and depends on map iteration order. For a vanilla pane's real textures, read
  `assets/<ns>/models/block/<pane_path>_post.json`'s `textures.pane` / `textures.edge`.
- **Backface culling.** `RenderTypes.translucentMovingBlock()` culls backfaces (its pipeline never calls
  `.withCull(false)`). Rotation preserves winding, so a rotated element can face away from the visible side.
  For panes, emit every quad twice: once as computed, once reversed with the negated normal.
- **Per-element rotation.** Blockbench allows `rotation: {x, y, z, origin}` on all three axes at once, unlike
  vanilla's model format.
- **Self-occlusion is not a bug.** A flipped (top-half) stair or slab can legitimately hide its own notch
  behind its overhang from normal eye-level angles, exactly like vanilla. If geometry looks right in debug
  logging but is invisible with the real host present, temporarily stub out the host's `submitMovingBlock`
  call. If the geometry then appears, it is occlusion, not a rendering bug.

## Vanilla beds are a special model, not a block model

Vanilla beds have no per-face block-model textures. `models/block/bed.json` is an empty stub (only a
`particle` texture), every state of `blockstates/<color>_bed.json` maps to it, and the geometry and texture
come from `BedRenderer` (a `BlockEntityRenderer`) reading `textures/entity/bed/<color>.png`. Item models are
`minecraft:special` with `type: minecraft:bed`. Per-face names like `bed_head_north` are pre-1.13 leftovers
that no longer exist.

Consequence for `camel-nostrils`' `UpsideDownBedBlock`: its blockstates point at vanilla's empty
`minecraft:block/bed` stub and its item models use the vanilla `special` bed model. The flip itself happens
in the renderer. `CN$BedRenderStateMixin` adds a duck field (`UpsideDownBedRenderStateDuck`, deliberately
outside the `mixin` package because Mixin refuses to load a plain interface from inside it) to
`BedRenderState`. `CN$BedRendererMixin` stamps that flag in `BedRenderer#extractRenderState` (TAIL) and
`@Redirect`s `modelTransform(Direction)` inside `submit` to compose an extra 180-degree rotation about the
head-to-foot axis, pivoted at the block center. It is a true rotation rather than a mirror or negative
scale, so face winding and culling stay intact. Per-color head/foot block-model JSONs for this block are
dead; if they reappear, that is stale state.
