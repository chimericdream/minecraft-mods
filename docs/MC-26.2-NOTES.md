# MC 26.2 port notes

Gotchas and non-obvious API changes hit while porting the mods to Minecraft 26.2 (from 26.1.2, and from
the earlier Yarn/1.21.x line). Not exhaustive — see `docs/history/UPDATE-PLAN.md` for the migration runbook.

## Datagen: "Components not bound yet"

Item data components are bound **lazily during a `ReloadableServerResources` reload**, not at
bootstrap. The `Item` constructor now just registers an initializer into
`BuiltInRegistries.DATA_COMPONENT_INITIALIZERS`; the map is baked and bound later. Datagen never
performs that reload, so any generator reading components at datagen time (e.g.
`Item.getDefaultMaxStackSize()`) throws `NullPointerException: Components not bound yet`
(`Holder$Reference.components`). **This is not a logic bug in the generator** — pre-26.2 code that
queried components during datagen silently broke on the update.

Fix — bind once, up front, the same way the server reload does. Put it at the **top of
`buildRecipes()`** (`minekea/fabric/.../data/ModDataGenerator.java`):

```java
BuiltInRegistries.DATA_COMPONENT_INITIALIZERS.build(registryLookup)
    .forEach(pending -> pending.apply());
```

`registryLookup` is the datagen `HolderLookup.Provider`. All APIs are public (no access widener).
Vanilla's `RegistryComponentsReport` and `ReloadableServerResources` use the same
`build(provider).forEach(PendingComponents::apply)` pattern. If another datagen provider (item models,
tags, loot) reads components before recipes run, hoist this bind earlier / into that provider. The unit-
test equivalent (baking components in JUnit bootstrap) is in `docs/TESTING.md`.

## Notable API renames (26.1.2 → 26.2)

Registry-constant holders moved into pluralized/util classes (mirroring the Blocks/BlockIds ID split).
The *type* classes keep their names; the **static-instance holders** moved:

- `BlockEntityType.X` → `BlockEntityTypes.X` (`net.minecraft.world.level.block.entity.BlockEntityTypes`). `BlockEntityType<T>` stays.
- `EntityType.X` (e.g. `VILLAGER`, `ITEM`) → `EntityTypes.X` (`net.minecraft.world.entity.EntityTypes`). `EntityType<T>` stays.
- `net.minecraft.advancements.CriteriaTriggers` → `net.minecraft.advancements.triggers.CriteriaTriggers`
  (predicates moved too: `advancements.criterion.*` → `advancements.predicates.*`).
- `LevelRenderer.getLightCoords(...)` / `LevelRenderer.BrightnessGetter` →
  `net.minecraft.util.LightCoordsUtil.getLightCoords(...)` / `LightCoordsUtil.BrightnessGetter`.
- `Minecraft.renderNames()` removed → HUD hidden = `Minecraft.getInstance().gui.hud.isHidden()`.
- `ValueInput.contains(String)` removed → `view.getString("k").isPresent()` (read with `getStringOr`/`getBooleanOr`).

### Color / copper collections

- Colored `Blocks.<COLOR>_<TYPE>` / `Items.<COLOR>_DYE` became `ColorCollection` fields with accessors
  `.white()`, `.lightGray()`, `.gray()`, `.black()`, `.brown()`, `.red()`, `.orange()`, `.yellow()`,
  `.lime()`, `.green()`, `.cyan()`, `.lightBlue()`, `.blue()`, `.purple()`, `.magenta()`, `.pink()`.
  Fields: `Blocks.WOOL`, `CARPET`, `CONCRETE`, `CONCRETE_POWDER`, `STAINED_GLASS`, `STAINED_GLASS_PANE`,
  `GLAZED_TERRACOTTA`, `DYED_TERRACOTTA` (⚠ `Blocks.TERRACOTTA` stays the plain block), `BANNER`,
  `WALL_BANNER`, `BED`, `DYED_SHULKER_BOX`, `DYED_CANDLE`, `DYED_CANDLE_CAKE`; `Items.DYE`. Already
  migrated in chimeric-lib `ColorHelpers`.
- Weathering copper collapsed into `WeatheringCopperCollection` fields:
  `Blocks.CUT_COPPER.weathering().unaffected()|exposed()|weathered()|oxidized()` and
  `.waxed().unaffected()|…`. `Blocks.COPPER_BLOCK` (plain) → `Blocks.COPPER_BLOCK.weathering().unaffected()`.

### Other removals/changes

- `net.minecraft.util.Tuple` **removed** → `com.mojang.datafixers.util.Pair` (`getA()`→`getFirst()`,
  `getB()`→`getSecond()`, `new Tuple<>(a,b)`→`Pair.of(a,b)`).
- Architectury 21.x `RegistrySupplier.getRegisteredName()` **removed** → `getId().toString()`. (Vanilla
  `Holder.getRegisteredName()` still exists — leave those.)
- `ItemStack(RegistrySupplier<Item>)` no longer resolves → call `.get()`.
- `EntityType.byString` removed → `Optional.ofNullable(Identifier.tryParse(id)).flatMap(BuiltInRegistries.ENTITY_TYPE::getOptional)`.
- `BlockPos.getCenter()` removed → `blockPos.distToCenterSqr(vec3)` for squared distance.
- `MenuScreens.register` + `MenuScreens$ScreenConstructor` are private → reach via access widener
  (Architectury 21.x `MenuRegistry` has no screen-factory helper). `TextureSlot.create(String)` is also
  private → access widener.
- `BlockAttachedEntity` (item frames, paintings, leash knots) save data: the old `TileX/TileY/TileZ`
  fields are gone, replaced by a single `block_pos` tag (`BlockPos.CODEC`, i.e. `[I;x,y,z]` in SNBT).
  `readAdditionalSaveData` does `input.read("block_pos", BlockPos.CODEC).orElse(null)`, and if that's
  `null` **or farther than 16 blocks from `this.blockPosition()` at the moment the check runs** it
  logs `"Block-attached entity at invalid position: {}"` and leaves the entity un-attached —
  `Facing` alone is no longer enough. The gotcha: for `/summon`, `Entity.load()` reads `readAdditionalSaveData`
  (and thus this check) **before** the command applies its positional x/y/z args — so unless the NBT
  *also* carries `Pos:[x.0d,y.0d,z.0d]` (`Vec3.CODEC`, read earlier in `Entity.load()`), the entity is
  still sitting at `(0,0,0)` when `block_pos` is checked, and the check always fails even though the
  frame ends up rendering in the right place afterward (the command's x/y/z still gets applied, just
  too late for this check). Any `/summon minecraft:item_frame ...` NBT (e.g.
  `minekea/demo-world/generate_layout.py`'s tool-showcase wall) needs **both**
  `Pos:[x.0d,y.0d,z.0d]` and `block_pos:[I;x,y,z]`, matching the summon coordinates.

### Datagen (Fabric) signature changes

- `TagAppender<T, T>` (two type args) → `TagAppender<T>` (single). Affects every
  `configureBlockTags`/`configureItemTags` signature.
- `TagAppender<T>.add(...)` now takes `ResourceKey<T>`, not the `Block`/`Item` object:
  `.add(BLOCK)` → `.add(BLOCK.builtInRegistryHolder().key())`;
  `.add(block.asItem())` → `.add(block.asItem().builtInRegistryHolder().key())`.
- `FabricTagProvider.valueLookupBuilder(TagKey<T>)` renamed to `builder(TagKey<T>)`.
- Predicate classes moved: `net.minecraft.advancements.criterion.{ItemPredicate,StatePropertiesPredicate}`
  → `net.minecraft.advancements.predicates.*`.

## Reading decompiled vanilla source

The 26.2 `-sources.jar` in the Loom cache is an **empty placeholder** (`genSources` was never run for
26.2). To read vanilla implementation code:

1. Use the binary jar (Mojang-mapped, merged, with Fabric `@Environment` annotations):
   `~/.gradle/caches/fabric-loom/minecraftMaven/net/minecraft/minecraft-merged-deobf/26.2/minecraft-merged-deobf-26.2.jar`
2. For signatures only, `javap -p` on the extracted `.class` is fastest.
3. For full bodies, decompile with Vineflower: download it from Maven Central (in Git Bash `curl` fails
   with exit 35 — use PowerShell `Invoke-WebRequest`), unzip the classes you need, then
   `java -jar vineflower.jar <classes> <outdir>`.

## The "Client shutdown from post-main" watchdog crash (spurious)

Since the 26.2 update, crash reports titled `Description: Client shutdown from post-main` /
`java.lang.Error: Watchdog (Client shutdown from post-main)` appear on client exit across several mods.
**These are not gameplay crashes and not bugs in this repo's code.** They fire from Mojang's
`ClientShutdownWatchdog` *after* `main()` returns: two non-daemon fixed thread pools
(`pool-1-thread-*`, `pool-2-thread-*`, sized to `availableProcessors()`) park idle in
`LinkedBlockingQueue.take()` and are never `shutdown()`, so the JVM can't exit and the watchdog
force-kills it. archaeology-tweaks and chimeric-lib were verified to create zero runtime threads — the
leak is in a shared dependency (architectury / fabric-api / YACL / modmenu / fabric-language-kotlin).
The game does fully close; impact is a spurious report + non-zero exit. Don't chase it in mod code.

## Build/datagen/GameTest tasks can hang after finishing (unlike the watchdog above, no self-kill)

Separately from the client-side watchdog crash above, a `./gradlew build`/`runGameTest`/NeoForge `run*`
task (datagen or otherwise) can finish all of its real work — compile, tests pass, world saved, "shutting
down" logged — and then just sit there indefinitely instead of exiting the JVM. Confirmed on both a
Fabric `runGameTest` (hopper-xtreme, 2026-08-27: log showed "All 24 required tests passed" and a clean
world save, then the process sat for 30+ minutes) and NeoForge `runData` (effective-gear, 2026-08-21: sat
25+ minutes after its last log line). Unlike the watchdog crash, **these do not self-terminate** —
nothing kills them for you, ever.

**Don't wait it out — check status every ~10 minutes, not every 20-30+.** The vast majority of
build/datagen/GameTest/run tasks finish in well under 10 minutes, so if a check still comes back "still
running" past that, treat it as a hang, not slowness. Poll the *expected output* (log tail, timestamps
on generated files, whether the jar/artifact already exists) rather than only waiting on the process or
backgrounded shell command to report completion — that's how to tell "still working" from "done but
stuck" without guessing.

**How to unblock:** once the output shows the real work already finished, find the stuck `java.exe`
(Windows: `Get-CimInstance Win32_Process -Filter "Name='java.exe'"`, cross-reference `CommandLine` to
pick the right one — e.g. the GameTest/run-config process, not an idle Gradle daemon you want to leave
alone) and `Stop-Process -Force` it. A subsequent build in the same session can fail with something like
"Failed to modify jar manifest" if the hung process still holds a file open — killing it resolves that
too.

## Multi-block structures: creative-mode breaking can still drop an item

For bed-like pairs (two `BlockState`s that reference each other, one half auto-removed via `updateShape`
returning air), vanilla's idiom in `playerWillDestroy` is `level.setBlock(otherPos, AIR, 35)`
(`UPDATE_NEIGHBORS | UPDATE_CLIENTS | UPDATE_SUPPRESS_DROPS`). That is **not enough**: it can still drop the
item in creative, depending on which half was clicked.

`Level#setBlock` strips `UPDATE_SUPPRESS_DROPS` before propagating the shape-update cascade to indirectly
affected neighbors (`updateFlags & -34`). Setting the other half to air makes the cascade reach back into the
half still being processed, which `Block.updateOrDestroy` then destroys with `destroyBlock(pos, true, ...)`,
dropping unconditionally.

Fix: add `Block.UPDATE_KNOWN_SHAPE` (16) to the flags (`UPDATE_NEIGHBORS | UPDATE_CLIENTS |
UPDATE_KNOWN_SHAPE | UPDATE_SUPPRESS_DROPS`). That skips the shape-update cascade for the call. Use this for
any new two-block structure. `jdcrafte:feeding_trough` was confirmed affected (flag 35 dropped on one break
order, flag 51 did not). Minekea's `ArmoireBlock` uses the bare-35 idiom and should be audited. A quick
regression check without a full GameTest: drive `player.gameMode.destroyBlock(pos)` and count nearby
`ItemEntity`s.

## Fabric datagen: dynamic registries and tags

1. **`RegistrySetBuilder.add(key, bootstrap)` in `DataGeneratorEntrypoint.buildRegistry()` writes no JSON on
   Fabric.** NeoForge auto-dumps every registry in the builder; Fabric needs an explicit
   `FabricDynamicRegistryProvider` per registry:
   ```java
   protected void configure(HolderLookup.Provider registries, Entries entries) {
       entries.addAll(registries.lookupOrThrow(Registries.VILLAGER_TRADE));
   }
   ```
   (references: `archaeology-tweaks`' `ArchaeologyTweaksWorldgenProvider` and `ArchaeologyTweaksVillagerTradeProvider`).
   Without it, `bootstrap()` runs with no error, but Fabric's cache pass treats the registry's files as
   stale and **deletes them** on every `runDatagen`, while NeoForge's `runData` alone produces them.
2. **A `TagKey` referenced in a bootstrap via `context.lookup(registry).getOrThrow(tagKey)` must resolve from
   a static, checked-in tag JSON**, not one a `FabricTagProvider` generates in the same run. Otherwise the
   tag does not exist yet, `getOrThrow` throws, and the failure is silently swallowed (no ERROR, normal
   "finished after Xms") with incomplete output. Hand-write the tag under
   `common/src/main/resources/data/<modid>/tags/<registry>/...json`.
3. **Fabric `runDatagen` and NeoForge `runData` race on the shared `common/src/main/generated` and its
   `.cache`.** Fabric's narrower view (no NeoForge-only registries such as biome modifiers) makes it delete
   NeoForge-only output as stale. Run the two as separate sequential invocations, NeoForge last, then check
   `git status` on the generated directory before trusting the result.

## 26.1.2 vs 26.2 differences (for the `26.1.2` branch)

Verified with `javap`, not inferred. **Absence rule:** `git grep <symbol> 26.1.2` only proves a symbol is
*used*, never that it is *absent*. To prove absence, extract the class from
`~/.gradle/caches/fabric-loom/minecraftMaven/net/minecraft/minecraft-merged-deobf/26.1.2/minecraft-merged-deobf-26.1.2.jar`
and run `javap -p` (or `-c -p` for call sites). `git show <rev>:<path>` applies eol conversion; use
`git cat-file blob` for raw bytes.

**Same on both (do not "fix" when backporting):** `SubmitNodeCollector` and the render-feature overhaul
(landed in 26.1); lazy data-component binding (`ItemStack` construction throws `Components not bound yet`, so
the JUnit bake and minekea's datagen bind are needed on 26.1.2 too; `DATA_COMPONENT_INITIALIZERS` has the same
shape); `net.minecraft.resources.Identifier`; `getStringOr` / `getIntOr`; `BlockBehaviour.Properties.noLootTable()`;
`com.mojang.datafixers.util.Pair` (prefer it over `net.minecraft.util.Tuple`, which still exists on 26.1.2,
so code does not diverge from `main`); `fabricApi { configureTests }`; Java 25.

**Different (26.1.2 on the right):**

| 26.2 | 26.1.2 |
|---|---|
| `new BlockEntityType<>(factory, blocks)` public | private. Widen it in the mod's own access widener, or in a fabric-only never-shipped source set use `FabricBlockEntityTypeBuilder.create(factory, blocks).build()`. |
| `GameTestHelper.makeMockServerPlayer(GameType)` | absent. `makeMockPlayer(GameType)` returns a plain `Player`; `makeMockServerPlayerInLevel()` returns a `ServerPlayer` whose `gameMode()` is hardcoded to CREATIVE. For a survival `ServerPlayer`, construct one directly (`server, level, GameProfile, ClientInformation.createDefault()`) and override `gameMode()`. |
| `EntityTypes.X`, `BlockEntityTypes.X` | `EntityType.X`, `BlockEntityType.X` |
| `Blocks.WOOL.white()`, `Items.DYE.red()`, `Blocks.DYED_TERRACOTTA.white()` | flat constants `WHITE_WOOL`, `RED_DYE`, `WHITE_TERRACOTTA`. The `DYED_` prefix is dropped for terracotta, shulker box, candle and candle cake. |
| `Blocks.CUT_COPPER.weathering().exposed()` | `Blocks.EXPOSED_CUT_COPPER` |
| `EntityType.byString(id)` removed | still present |
| `TagAppender<T>`, `FabricTagProvider.builder(...)` | `TagAppender<T, T>`, `valueLookupBuilder(...)` |
| `MenuScreens.register`, `TextureSlot.create` private | public, no access-widener entry needed |

## More 26.2 API changes (client, entities, predicates)

- Render feature overhaul: `MultiBufferSource` became `SubmitNodeCollector`.
  `OrderedSubmitNodeCollector.submitModelPart(part, pose, renderType, light, overlay, sprite, int color,
  CrumblingOverlay, int outline)` dropped its two `boolean` args; `submitNameTag(...)` dropped its
  `double squaredDistanceToCamera`; `RenderType` moved to `net.minecraft.client.renderer.rendertype`.
- `EntityType.loadEntityRecursive(nbt, level, EntitySpawnReason, proc)` now takes a wrapped reason:
  `new EntitySpawnRequest(EntitySpawnReason.X, false)`.
- `EntityPredicate` is map-based: `EntityPredicate.Builder.entity().nbt(x)` is gone; use
  `.put(EntityNbtPredicate.CODEC, new EntityNbtPredicate(nbtPredicate))`. Packages:
  `net.minecraft.advancements.predicates.entity` (EntityPredicate), `net.minecraft.advancements.predicates`
  (NbtPredicate).
